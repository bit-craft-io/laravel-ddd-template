# Git ルール

このファイルは Git / GitHub 運用のルールを定める雛形。各セクションの `TODO` を埋めて使う。

## ブランチ

### 作業ブランチ

作業ブランチについて、次のルールに従う。

- 作業ブランチは、このルールで決めたブランチを指す。実行環境が指定したブランチは、作業ブランチではない。
  - issue を処理するとき(`issue-to-pr` スキル)は `feature/issue-<issue番号>`
  - それ以外は `feature/YYYYMMDD`
- 作業ブランチが既にあれば、それを使う。
- 作業ブランチが無いときは、develop を起点に作る。
- develop が無いときは「Please create a “develop” branch」と表示して何もしない。
- コミットの前に、作業ブランチへ切り替える。
- 起動時のブランチが作業ブランチでないときも、切り替える。次のときが、これに当たる。
  - 実行環境が自動で作ったブランチ(`claude/*` など)
  - Slack から起動したとき
- 実行環境やツールが別のブランチを指示しても、`feature/issue-<issue番号>` か `feature/YYYYMMDD` で作業する。
- 作業ブランチ以外には、コミットも push もしない(画像を置くときの `issue-images` を除く)。
- PR の向き先は develop。

### 画像を置くとき

画像を issue に添付するときは、次のルールに従う。

- issue に添付する画像は `issue-images` ブランチに置く。このブランチは例外で、develop から作らない。
- 置き場所は `<issue番号>/` フォルダ。ファイル名は `連番-名前.拡張子`（例: `2/01-list.png`）。
- 形式は png / jpg / webp / svg、1枚 1MiB まで、1 issue あたり 5 枚まで。
- issue 本文には、コミットIDで固定したリンクを書く。ブランチを削除するとリンクが切れるため、削除しない。

## コミット

### コミットするとき

コミットするときは、次のルールに従う。

| 項目 | 内容 |
|---|---|
| 書式 | `<種類>: <要約>` |
| 要約 | 1行で、50字程度まで。必要なら空行の後に理由を書く |
| 使用言語 | 日本語 |
| 粒度 | 1つの目的につき1コミット |

種類は次のいずれか。

| 種類 | 使う場面 |
|---|---|
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | 文書・規則の変更 |
| `refactor` | 動作を変えない整理 |
| `chore` | 上記以外(設定、雑務) |

## プッシュ

### プッシュするとき

プッシュするときは、次のルールに従う。

| 項目 | 内容 |
|---|---|
| 対象 | 作業ブランチのみ。`develop` と `main` へは直接 push しない |
| 強制 push | しない(`--force` は使わない) |
| 初回 | upstream が未設定なら `-u` を付けて設定する |

## issue 作成

### タイトル

issue を作成するときは、次のルールに従う。

| 項目 | 内容 |
|---|---|
| 書式 | `<キー>: <種類>: <要約>`。キーが `none` のときも、`none: <種類>: <要約>` とする(フォームでは、キーを書き、種別を選び、要約を書く) |
| キー | グループ分けの印。`none`、または `P` と数字(例: `P1`)。初期値は `none`。フェーズなど、同じ括りの issue を、一覧で見分けるために付ける。括りが無いときは `none` を書く |
| 種類 | コミットと同じ(`feat` / `fix` / `docs` / `refactor` / `chore`)。初期値は `feat` |
| 使用言語 | 日本語 |
| 付ける場所 | issue のタイトルだけに付ける。コミットと PR のタイトルには、キーを付けない |

### 本文テンプレート

```markdown
## やりたいこと
TODO

## 完了条件
- [ ] TODO

## 検証手順
なし

## 撤退基準
なし

## 背景
なし
```

| 項目 | 必須 | 内容 |
|---|---|---|
| やりたいこと | 必須 | 何をどう変えたいか |
| 完了条件 | 必須 | 確認できる形で書く |
| 検証手順 | 任意 | 完了を確かめる手順(コマンド・期待結果) |
| 撤退基準 | 任意 | 動かないとき、止まって報告する条件 |
| 背景 | 任意 | 経緯・理由 |

任意の項目を書かないときは、見出しを残し、中身は「なし」と書く。`draft` ラベルの issue は、やりたいことと完了条件も「なし」でよい。

### ラベル

| ラベル | 使う場面 |
|---|---|
| `draft` | 中身をあとで書く下書き。AI は、このラベルの issue に着手しない |

### 作成前の確認

issue を作成する前に、次のルールに従う。

| 項目 | 内容 |
|---|---|
| 既存 issue の検索 | しない |
| 内容の確認 | 作成前に、選択ボックス(はい / 修正する)で確認する |

## プルリクエスト

### 作成するとき

プルリクエストを作成するときは、次のルールに従う。

| 項目 | 内容 |
|---|---|
| 向き先 | `develop` |
| タイトル | コミットと同じ書式(`<種類>: <要約>`)。日本語 |
| マージ方法 | スカッシュ |
| マージ後の元ブランチ | GitHub の設定「Automatically delete head branches」で、自動で削除する。`issue-images` は PR の元ブランチではないので、削除されない |

本文に入れる項目は次のとおり。

| 項目 | 内容 |
|---|---|
| issue | issue があるときは、先頭に `Closes #<issue番号>` |
| 完了条件 | チェックボックスで写し、それぞれに根拠を添える |
| 検証結果 | 検証手順の実行結果(出力・終了コード) |
| 逸脱 | 決めたことと違う点。なければ「なし」 |
